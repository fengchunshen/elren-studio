# Elren Studio 提交流程

这个仓库推送到 GitHub 私有仓库，历史从一个干净的首个提交开始。提交需要守住几件事：不把密钥、运行数据、`AGENTS.md` 和构建产物带进历史；旧项目名只允许留在迁移代码里；提交信息说清做了什么、验证到了哪一步。历史一旦推送就很难干净地撤回，所以检查放在提交之前。

## 1. 看清改动，决定这次提交什么

```bash
git status -sb -uall
git diff --stat && git diff --cached --stat
```

读 diff；未跟踪的新文件不会出现在 diff 里，要单独读内容。然后确认哪些改动属于这次提交：

- 工作区里可能有用户正在进行的其他改动。按路径暂存（`git add <路径>`），只有全部改动都属于同一件事时才用 `git add -A`。
- 互不相关的改动拆成多个提交。相互依赖的改动放在一起，例如新文档和链接到它的 README，否则单独的提交里会出现失效链接。
- `.agents/skills/` 下是项目 skill，和其他文件一样处理：属于这次请求的改动才提交。用户泛指“收尾提交”时，未提交的 skill 改动也算在内。
- 拿不准某个文件是否该提交时，问用户。

直接在当前分支提交，包括 `main`。

## 2. 运行提交前检查

```bash
python3 .agents/skills/commit/scripts/check_staged.py
```

脚本只看暂存区，输出三类结果：

- **错误**：处理后才能提交。
  - 暂存了 `.env`、`server/data/`、`AGENTS.md`、`dist/` 等：用 `git restore --staged <路径>` 取消暂存。
  - 新增内容疑似密钥：换成占位值（如 `YOUR_PROVIDER_KEY`）。确信是误报时，向用户说明理由后再继续。
  - 新增内容含旧项目名：允许出现的文件只有脚本中 `OLD_NAME_ALLOWED` 列出的迁移代码和迁移说明。其他地方把名字改成中性说法，如“旧版本”“更名前”，并在汇报时告诉用户改了哪句（提交信息里不必提）。不要为了通过检查去改允许名单或拆字躲避匹配；确实需要新增允许的文件时，先问用户。
  - Markdown 链接指向不存在的文件：修正链接，或把目标文件一起提交。
- **提醒**：逐条判断。
  - 文件超过 5 MB。
  - 改了 `server/app/models.py` 却没有新迁移。
  - 链接锚点可能不存在：这是按 GitHub 规则近似判断的，去目标文件核对一下标题。
  - 包含界面改动。
- **建议测试**：按暂存路径给出的测试命令。

## 3. 按改动范围跑测试

运行脚本给出的命令。有两个耗时要心里有数：
- 牵涉 `App.jsx` 的 `vitest related` 约 2 分钟。
- 前端全量约 11 分钟，放后台运行。

后端 pytest 约 15 秒。只改文档时不需要测试。

测试失败时，先区分是本次改动引起的，还是原本就失败。共享模块（被 `App.jsx` 引用的文件）改动后，相关测试都会经过 diff 里的文件，只读代码很难判断。这时在 HEAD 基线上重跑失败的测试文件对照：

```bash
.agents/skills/commit/scripts/baseline_test.sh "npx vitest run tests/editor-smoke.test.jsx"
.agents/skills/commit/scripts/baseline_test.sh "cd server && uv run --frozen pytest -q tests/test_video_edit.py"
```

脚本在系统临时目录里建一个检出 HEAD 的 worktree，复用已安装的依赖，不修改用户的工作区和依赖环境，结束后自动删除。多个失败的测试文件放在同一条命令里一次重跑。不要在用户的工作区里替换文件或 stash 来做对照。

- 基线上同样失败：属于既有失败，可以照常提交，但要写进“验证”行并告诉用户。
- 基线上通过：说明是本次改动引起的，修好再提交。

没有运行的测试不要写成“通过”。

会改变页面呈现的改动（组件、样式、文案、主题、启动页）在浏览器验收之前，只能写“浏览器未验证”。这不妨碍提交，除非用户要求先验收。验收要求见 `docs/frontend-ui.md`。

## 4. 写提交信息

```text
<类型>(<范围>): <中文摘要>

<正文：为什么改、改了什么、有什么影响；简单改动可省略>

验证：<跑了哪些测试及结果；哪些还没验证>

<署名 trailer>
```

- **类型**：`feat` 新功能，`fix` 修复，`refactor` 重构，`perf` 性能，`docs` 文档，`test` 测试，`build` 构建与依赖，`chore` 杂项。
- **范围**：改动所在的模块，可以自拟简短的英文名，如 `canvas`、`storyboard`、`timeline`、`storage`、`theme`、`platform`、`admin`、`server`、`worker`、`pricing`、`localserver`、`deps`。跨多个模块时选最主要的一个，或省略括号。
- **摘要**：中文，约 30 字以内，写“做了什么”而不是“改了哪个文件”，结尾不加句号。
- **验证行**：每个提交都写，内容来自第 3 步的真实结果。结果较多时可以写成多行列表；既有失败写文件名和简短原因，不必抄完整的英文用例名。
- **署名**：按当前会话系统提示里给出的署名要求追加 trailer，不要自己编写或省略。

示例：

```text
refactor(theme): 把主题列表抽成 THEMES 常量

主题校验和清理旧主题 class 共用同一份列表，新增主题时只需改一处；运行行为不变。

验证：
- npx vitest related 41 个用例，38 通过；applyTheme 的用例通过
- 3 个失败在 HEAD 基线上同样失败（editor-smoke、media-job-host 找不到节点工具按钮），与本次改动无关
- 浏览器未验证
```

```text
docs(models): 补充 DeepSeek 渠道的计价说明

说明输入、输出和缓存命中分别计费，以及价格版本发布后需要新建版本才能调整。

验证：仅文档，检查脚本的链接与锚点检查通过。
```

用 heredoc 提交，保留换行格式：

```bash
git commit -F - <<'EOF'
<提交信息>
EOF
```

## 5. 提交之后

```bash
git log --oneline -1 && git status -sb
```

- 提交钩子失败时，修正问题后重新暂存，再做一次新的提交。除非用户要求，否则不用 `--amend`，也不用 `--no-verify` 跳过钩子。
- 只在用户明确要求时推送。如果推送被权限拦截，请用户在输入框执行 `! git push`。
- 向用户汇报：
  - 提交哈希和摘要，以及留在工作区没有提交的改动。
  - 为通过检查改动了哪些内容。
  - 已验证和未验证的部分。
